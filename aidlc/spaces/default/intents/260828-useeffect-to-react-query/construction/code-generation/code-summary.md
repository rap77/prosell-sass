## Key implementation decisions

1. **`retry: false` on `useMyOrganization()`** — the original `useEffect` made exactly one attempt and treated any failure as "no organization yet, show the wizard." TanStack Query's default retry (3 attempts with backoff) would have delayed that fallback for new users, changing FR1.2's "preserve observable behavior." Explicitly disabling retry keeps the timing identical.
2. **`setup_complete` redirect stays a `useEffect`** — this is a navigation side-effect reacting to already-fetched data, not the data-fetching effect itself, so it does not reintroduce the `AGENTS.md:333` violation the requirement is fixing.
3. **`react-hooks/set-state-in-effect` suppressor removed** (FR2.4/OQ1: resolved) — the new effect never calls `setState` synchronously in its body. The "no token" case is now a pure derived value (`state`/`message` computed from `token`/`mutation`/`errorState`, not stored in `useState`), and the "token present" path only calls `mutation.mutate(...)`, whose `onSuccess`/`onError` run as async completions, not synchronously during the effect. No suppression comment remains anywhere in the file.
4. **Anti-double-fire guard uses `mutation.status !== "idle"`**, not a `useRef` flag — this is correct even under React 18 Strict Mode's dev double-invoke because `useMutation`'s internal state persists across the effect's cleanup+rerun for the same mounted component instance, so the second invocation sees a non-idle status and bails.
5. **Dropped the dead `setTeamName`/`teamName` state** in `invite/[token]/page.tsx` — the original set it but never rendered the value anywhere; removing it is not an observable-behavior change.
6. **`useAcceptInvitation()` and `useMyOrganization()` deliberately have no `onError`/`onSuccess` inside the hook** — `useAcceptInvitation()`'s caller-side `onError` needs the raw thrown `ApiError` (with `.status` and `.message`) to reach it unchanged for the expired/already-member/401 branching (FR2.3); wrapping or rewrapping the error inside the hook (the `notificationsApi.ts` pattern, which throws a generic `Error`) would have broken that branching, exactly as flagged in reverse-engineering.
7. **Neither hook touches `fetchWithAuth`** — per requirements.md C1, the pre-existing gap (no auto-refresh-on-401 in `orgApi`/`teamApi`) is left as-is; both hooks call the existing raw-fetch methods unchanged.
