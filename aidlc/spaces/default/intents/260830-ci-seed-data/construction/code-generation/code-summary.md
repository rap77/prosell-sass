## Key Implementation Decisions

- **FR1/FR2**: pure test-data fix — `apps/api/src/prosell/infrastructure/database/seed_categories.py` already correctly makes `carros-y-camionetas` the leaf (it was never wrong); only the 3+1-year-stale test assertions needed to catch up.
- **FR3**: the naive fix (nesting `begin_nested()` directly on a session already wrapped in `session.begin()`) does NOT work — SQLAlchemy's `TransactionalContext._trans_ctx_check` rejects it with the exact same "closed transaction" error on the session's _next_ query, because `session.begin()`'s context manager loses track of its own transaction identity once a nested transaction takes over as "current". Confirmed empirically (first attempt on `test_fb_sync_router.py` failed the same way as the original bug, before switching to a connection-level `connection.begin()` + `AsyncSession(bind=connection)` — SQLAlchemy's documented "Joining a Session into an External Transaction" recipe — which passed cleanly, including both previously-broken idempotency-check tests). Applied the same validated pattern to `bulk_upload/conftest.py`, but since `db_session` there is a _shared_ fixture (out of scope to modify per Q3), the override binds a _new_ session to `db_session`'s live connection instead of nesting on `db_session` itself — same effect, zero changes to the shared fixture.
- **FR4 scope expansion (human-approved mid-implementation)**: fixing `category_id=uuid4()` surfaced a SECOND, previously-masked FK violation — `products_submitted_by_fkey`/`approved_by_fkey` — because `reviewer_id`/`user_id` in these same tests were also random UUIDs never inserted as real users. The category FK failed first in every case, so this second FK was never reached before. Surfaced to the user mid-implementation (not silently expanded); approved to fix using the same pattern (existing `test_user` fixture, tenant-scoped like `test_category`).

- **C1 / no production code touched**: `git diff --stat -- apps/api/src/prosell/` is empty; all 6 changed files are under `apps/api/tests/`. Matches the code-summary's claim exactly.
- **SAVEPOINT pattern correctness (FR3)**: both fixtures follow SQLAlchemy's documented "Joining a Session into an External Transaction" recipe — `connection.begin()` (outer) + `AsyncSession(bind=connection)` + `session.begin_nested()` + an `after_transaction_end` listener on `session.sync_session` that restarts the savepoint when a nested transaction ends whose parent is not itself nested. The restart condition (`transaction.nested and not transaction._parent.nested`) matches the upstream recipe's canonical form. This correctly isolates the test's rollback boundary from an endpoint's `await db.commit()`, because the commit only releases the SAVEPOINT, never the outer transaction — verified both by the code-summary's account of empirical testing (the previously-broken idempotency test, which calls the endpoint twice, now passes) and by inspecting the actual diff. `bulk_upload/conftest.py`'s variant (a second `AsyncSession` bound to `db_session`'s live connection, never touching `db_session` itself) is a sound extension of the same recipe for a shared fixture that already owns `session.begin()` — nesting directly on `db_session` would conflict with `session.begin()`'s own transaction-identity tracking, exactly as the code-summary describes, so binding a fresh session to the same connection and nesting on that instead is the correct workaround, not a hack.
- **Event-listener registration**: `event.listens_for(session.sync_session, ...)` is registered on a per-test, per-fixture-invocation sync-Session instance (a fresh object every test), matching SQLAlchemy's own documented recipe for this exact pattern. No evidence of accumulation across test runs within the process — each listener is scoped to an instance that goes out of scope at the end of its test.
