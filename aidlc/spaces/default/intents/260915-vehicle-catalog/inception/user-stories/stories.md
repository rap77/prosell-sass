# User Stories — Catálogo Canónico de Vehículos para Facebook

Persona: Admin de Dealership/Organización (`personas.md`). Basado en `requirements.md` (FR1, FR2).

## US1 — Reconciliación de catálogos de valores de Facebook (← FR1)

### US1.1 — Autocompletado de VIN con valores canónicos

**Como** Admin de Dealership, **quiero** que al decodificar el VIN los campos del formulario se completen con valores que Facebook ya acepta, **para que** mis publicaciones no sean rechazadas por un mapeo incorrecto de categoría o atributo.

**Priority**: Must Have

**Acceptance Criteria**:

- **AC1.1.1**: Given un VIN válido cuyo valor decodificado para un campo (ej. `body_type="suv"`) tiene una correspondencia conocida en el catálogo canónico, When lo ingreso y el sistema lo decodifica, Then el campo se completa con la opción EXACTA correspondiente a ese valor decodificado (no solo con alguna opción válida cualquiera del catálogo) — mismo rigor ya exigido en el precedente `260911-cross-org-export-ux` para bugs de valor, no solo de clave.
- **AC1.1.2**: Given un campo cuyo valor decodificado no tiene una opción correspondiente en el catálogo canónico, When se autocompleta el formulario, Then ese campo específico queda vacío (con una marca visual distinta a "campo sin dato", ej. un indicador de "no se pudo autocompletar") para que yo lo complete a mano, y el resto del formulario no se bloquea.
- **AC1.1.3**: Given que ingreso a mano un valor de atributo que no calza con ninguna opción configurada del schema, When intento guardar el vehículo, Then el sistema rechaza el guardado con un error que indica qué campo no es válido.
- **AC1.1.4**: Given un valor YA reconciliado que provino del decode de VIN (ej. `body_type="SUV"`, la opción exacta de AC1.1.1 — no tipeado a mano), When `Category.validate_attributes()` lo valida al guardar, Then pasa la validación sin error — cubre el piso de test #2 de `team-practices.md` desde el lado del dato normalizado, no solo desde el valor tipeado a mano de AC1.1.3.

**INVEST**: Independiente de US1.2 y de US2; entrega valor por sí sola (evita publicaciones mal categorizadas); estimable y chica (un flujo de decode + reconciliación); testeable vía los 4 AC de arriba (piso de test #1 y #2 de `team-practices.md`).

### US1.2 — Sincronización del editor de schema con el catálogo de valores

**Como** Platform Admin, **quiero** que el editor de schema de categorías cargue valores directamente del catálogo de Facebook vigente, **para** no tener que mantener dos listas de valores a mano sin garantía de que coincidan.

_Corrección aplicada (ronda 1, señalada por design, verificada contra código real): esta historia se reasignó del Admin de Dealership al Platform Admin — `category_router.py` gatea explícitamente el editor de schema a `super_admin` (`_require_platform_admin()`), y el tenant admin lo tiene bloqueado (`test_tenant_admin_cannot_patch_schema()`). Ver `personas.md`._

**Priority**: Must Have

**Acceptance Criteria**:

- **AC1.2.1**: Given el editor de schema de categorías con un campo mapeado a una clave conocida del catálogo de Facebook (ej. `fuel_type`), When cargo valores desde el catálogo para ese campo, Then las `options` resultantes son exactamente el conjunto de valores vigente en el catálogo para esa clave — ni un valor de más ni de menos, sin edición manual posterior para que coincidan.

**INVEST**: Independiente de US1.1 (mismo grupo, sin dependencia de secuencia); valiosa por separado (reduce deuda de mantenimiento, no solo corrige el decode); chica y testeable (piso de test #3 de `team-practices.md`).

## US2 — Defaults de ubicación editables por producto (← FR2)

### US2.1 — Editar la ubicación de un producto específico

**Como** Admin de Dealership, **quiero** editar la ubicación de un vehículo específico, **para que** ese producto muestre y publique una ubicación distinta a la de mi organización cuando corresponda.

**Priority**: Must Have

**Acceptance Criteria**:

- **AC2.1.1**: Given el detalle de un producto existente, When edito y guardo una ubicación específica para ese producto, Then esa ubicación queda persistida a nivel del producto — no solo calculada en el momento de exportar.
- **AC2.1.2**: Given un producto sin override de ubicación, When lo veo en creación/edición, Then muestra la ubicación default heredada de mi organización, distinguida visualmente de un override ya guardado (ej. una etiqueta "heredado de organización" vs. sin etiqueta cuando hay override) — sin esa distinción no puedo saber si lo que veo es el default o algo que ya edité antes.
- **AC2.1.3**: Given un producto CON override de ubicación guardado, When se exporta al catálogo cliente, Then el CSV usa la ubicación del producto, no la de la organización — mismo comportamiento de prioridad ya implementado en el export, sin cambios.
- **AC2.1.4**: Given que estoy creando un producto nuevo, When ingreso una ubicación distinta a la default de mi organización antes de guardar por primera vez, Then esa ubicación se persiste como override del producto desde su creación — no solo en ediciones posteriores. Cubre explícitamente FR2.2 ("se aplica en creación y edición"), que AC2.1.1 por sí sola solo cubría para edición.
- **AC2.1.5**: Given que intento guardar un override de ubicación vacío o inválido (ej. ciudad sin estado), When guardo, Then el sistema rechaza el valor inválido con un error, y un valor vacío revierte al default de la organización en vez de persistir un override vacío [assumption — ver `## Assumptions & Open Questions`] — mismo criterio de validación ya aplicado a otros campos obligatorios del formulario de producto.

**INVEST**: Independiente de US1 (grupo de trabajo distinto, sin dependencia); valiosa (el admin gana control fino sin tener que cambiar la ubicación de toda la organización); chica — el backend ya persiste y prioriza `location_city`/`location_state` por-producto en creación, edición y export (verificado contra código real por developer); el trabajo real de esta historia es la UI de edición, no lógica de dominio nueva; testeable vía los 5 AC de arriba.

## Dependencies

- US1.1 y US1.2 pertenecen al mismo grupo de trabajo (FR1) pero son independientes entre sí — ninguna bloquea a la otra.
- US2.1 es independiente de todo el grupo US1 — pertenece a un grupo de trabajo distinto (FR2) del backlog ya confirmado en `scope-document.md`.
- Ninguna historia de este documento depende de FR3 (migración legacy) o FR4 (documentación de publisher) — no generan historias de usuario propias.
- El piso de test #4 de `team-practices.md` (tabla de traducción de categorías, `CATEGORY_TRANSLATION_TABLE`) tampoco genera una historia propia — es cobertura de test de un domain service interno sin interacción de usuario nueva, igual criterio que FR3/FR4. Ver `traceability.json` para su marca explícita.
- **Nota de developer (ronda 1, verificado contra código real)**: el backend ya persiste y prioriza `location_city`/`location_state` a nivel de producto en creación, edición, y en el fallback del export — la pieza que falta para US2.1 es únicamente el input de UI en el formulario de producto, no lógica de dominio nueva. Functional Design no debería diseñar trabajo de backend nuevo para esta historia.
