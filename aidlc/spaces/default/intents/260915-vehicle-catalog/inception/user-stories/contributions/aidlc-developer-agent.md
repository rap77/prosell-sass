### 3. FR sin historia — ¿es correcto?

FR3 (migración legacy) y FR4 (documentación de contrato) están correctamente excluidos: son trabajo de backend/datos y documentación sin interacción de usuario nueva — mismo criterio ya usado en intents previos para migraciones de datos y para trabajo de documentación pura. FR5 (sanitización CSV) también está correctamente excluido: es un cambio defensivo que, por diseño (FR5.1 dice explícitamente "sin cambiar el valor visible para el cliente"), no altera ninguna interacción ni ningún valor observable del flujo de export ya existente — no hay una historia de usuario genuina que redactar ahí sin forzarla.

**Gap real encontrado**: FR2.2 dice explícitamente "El override de ubicación por producto se aplica en creación y edición de producto — no solo en el momento de exportar", pero AC2.1.1 solo cubre el flujo de EDICIÓN ("Given el detalle de un producto, When edito y guardo..."). No hay ningún AC que cubra explícitamente "Given que estoy CREANDO un producto nuevo, When ingreso una ubicación específica y guardo, Then queda persistida desde la creación" — AC2.1.2 menciona "en creación/edición" pero solo para el caso de MOSTRAR el default, no para el caso de EDITAR/fijar un override durante la creación misma. Si el formulario de creación y edición es el mismo componente (`UnifiedProductForm.tsx`, reutilizado en ambos flujos per el patrón ya documentado de "generic product form"), es probable que agregar el campo lo resuelva de forma automática — pero el AC tal como está redactado no lo prueba explícitamente, y FR2.2 lo pide de forma explícita como sub-requisito propio. Recomiendo agregar un AC2.1.4 (o extender AC2.1.1) que cubra el flujo de creación por separado.
