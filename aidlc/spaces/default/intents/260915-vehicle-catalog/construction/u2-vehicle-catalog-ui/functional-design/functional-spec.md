# Functional Spec — U2 (`u2-vehicle-catalog-ui`)

Unit kind `ui` — sin `entities.md`/`rules.md` propios (produces_kinds de esta etapa los excluye para `kind: ui`); este archivo es autocontenido, derivado de `unit-of-work.md`, `requirements.md`, `contract-summary.md` y de los artefactos ya aprobados en Refined Mockups (`mockups.md`, `interaction-spec.md`, `design-system-mapping.md`, `accessibility-checklist.md`).

## Workflow 1 — Autocompletado de VIN con indicador de mismatch (← US1.1)

1. El usuario ingresa un VIN en `VinDecodeField` (renderizado por `SchemaFieldRenderer.tsx`, bloque `render_as: "vin_decode"` — corrección post-revisión, no un componente `CanonicalSelectField` sobre `GenericFormFields` inexistente).
2. El formulario llama al Contrato 1 (`POST /vehicles/decode-vin`, ya extendido por U1 con `unmatched_fields`) — requiere extender `DecodeVinResponseSchema`/`useDecodeVin()` para no descartar ese campo (ver `frontend-components.md` § 1, mecanismo completo).
3. `mapDecodedToForm(decoded, schema, setValue, unmatchedFields)` recorre el schema: para cada campo con match, `setValue(key, canonical_value)` completa el campo normalmente (AC1.1.1); para un campo sin match (`value === null`), ya no se llama `setValue` — el campo queda vacío (comportamiento ya existente, sin cambios) — y además se escribe `setValue("_unmatchedFields", unmatchedFields)`, el canal RHF virtual que el paso 4 lee.
4. En el bloque `type: "select"` de `SchemaFieldRenderer`, `useWatch("_unmatchedFields")` deriva si ese `fieldKey` está en la lista — si sí, se muestra el ícono de ayuda "(i)" + texto "No se pudo autocompletar — completar a mano" junto al `SelectControlled` (AC1.1.2).
5. Si el usuario completa a mano un valor que no calza con ninguna opción configurada del schema y guarda: error inline junto al campo, no se guarda (AC1.1.3 — comportamiento de `Category.validate_attributes()`, sin cambios, ya cubierto por U1/BR1.3).

## Workflow 2 — Editor de schema de categorías consumiendo el catálogo canónico (← US1.2)

1. Platform Admin abre el editor de schema de una categoría (`category-schema-editor.tsx`, ya gateado a Platform Admin del lado de la UI).
2. Para cada `row.key` del schema: si `row.key` pertenece al vocabulario de vehículo cubierto por `FacebookVehicleValueCatalog` (`make`, `fuel_type`, `transmission`, `body_type`, `drivetrain`, `wheelbase_type`, `bed_type`, `cab_type`, `electrification_level`), se llama a `GET /categories/facebook-values/{row.key}` (Contrato 2) usando `row.key` directamente como `field_key` — SIN pasar por `FACEBOOK_FIELD_KEY_MAP` (Q1 de esta etapa, opción A: el vocabulario ya coincide carácter a carácter).
3. Las `options` del campo se pueblan con la respuesta exacta del endpoint (AC1.2.1) — ni una opción de más ni de menos.
4. Si el endpoint devuelve 404 (field_key sin catálogo — no debería ocurrir para los 9 campos listados, sería un bug de configuración de U1): el campo cae al comportamiento actual (input manual de "Options"), igual que hoy para cualquier campo sin `FacebookFieldKey` mapeado.
5. Para `row.key` que NO pertenece al vocabulario de vehículo (`category`, `item_state`, `platform`, `device`, `brand` de otros verticales, colores, etc.): comportamiento sin cambios — `FACEBOOK_FIELD_KEY_MAP`/`facebook-values/index.ts` (catálogo estático) sigue siendo la fuente, tal como hoy.

## Workflow 3 — Editar ubicación por producto (← US2.1)

1. El usuario abre el detalle de un producto existente.
2. La vista muestra dos campos de texto — Ciudad y Provincia (`ProductLocationFields`, `interaction-spec.md`) — con los valores actuales (override del producto si existe, si no el default de la organización).
3. Si AMBOS campos muestran el default de organización (sin override guardado): aparece el badge "Heredado de organización" (AC2.1.2).
4. El usuario edita uno o ambos campos y guarda:
   - Si completa AMBOS (ciudad y provincia): se persiste el override a nivel de producto (AC2.1.1, AC2.1.4 si es creación), el badge desaparece.
   - Si completa solo UNO de los dos, o deja ambos vacíos habiendo tenido antes un override: error inline, se revierte al default de organización sin persistir un override parcial o vacío (AC2.1.5).
5. Al exportar el catálogo, la prioridad ya existente (override del producto > default de organización) sigue sin cambios (AC2.1.3) — sin trabajo nuevo de backend, ya verificado por developer en `stories.md`.
