## Decisiones clave de implementación

- **Vocabulario de `field_key` = attribute_schema/VIN-decode, NO `FacebookFieldKey`** (ya fijado y revisado READY en `entities.md`/`rules.md` de esta etapa) — el catálogo cubre exactamente `make`, `fuel_type`, `transmission`, `body_type`, `drivetrain`, `wheelbase_type`, `bed_type`, `cab_type`, `electrification_level`, verificado carácter a carácter contra `nhtsa_normalizer.py` y `vehicle_router.py`.
- **`accepted_raw_aliases` = identidad del `canonical_value`**: cada entrada del catálogo tiene un único alias, igual a su propio `canonical_value`. Esto es correcto y suficiente para BR1.1/BR1.2 (el flujo de decode de VIN en tiempo real) porque `NHTSA_TO_FACEBOOK` ya colapsa toda variante de entrada NHTSA a un único token normalizado antes de que este servicio lo vea — verificado con el test de reconciliación cruzada al 100%. Ver la sección "Desviaciones" para la implicación sobre BR3.1.
- **BR3.1 implementado como migración Alembic real** (no script ad-hoc separado), per la corrección de Infrastructure Design — mismo mecanismo que su precedente citado (`20260812_0002_migrate_legacy_sedan_products.py`), con `downgrade()` real (no "sin rollback automatizado" como decía el borrador original de `cicd-pipeline.md`).
- **Downgrade simétrico sin tabla de auditoría nueva**: el valor pre-migración se guarda en un marcador (`_pre_migration_<field_key>`) dentro del mismo `attributes` JSONB del producto, no en una tabla separada — consistente con NFR-SEC-4 ("sin diseño de encriptación/almacenamiento nuevo, los datos no son sensibles") y con la guía de `project.md` (preferir logging/mecanismos ligeros sobre tablas de auditoría dedicadas cuando no hay precedente para ese dominio).
- **Log de la migración sin valores de atributo en texto plano**: ajustado durante Code Generation (ver Desviaciones) para cumplir literalmente NFR-SEC-4/`security-design.md` ("nunca el valor de atributo completo en texto plano") — el log de resumen registra `product_id` + `field_key` + razón de exclusión, nunca el valor capturado ni el nuevo valor.

## Desviaciones del plan (documentadas, no resueltas en silencio)

1. **Path de test de `csv_export.py`**: el plan (`code-generation-plan.md` Step 8, `unit-test-instructions.md`) cita `apps/api/tests/unit/domain/services/test_csv_export.py` — ese archivo NO existe. El archivo real (verificado con `fd`) es `apps/api/tests/unit/services/test_csv_export.py`, ya con 30 tests de intents previos (`260903-catalog-client-export`, `260911-cross-org-export-ux`) para el mismo módulo. Extendí el archivo REAL en vez de crear un duplicado — consistente con la regla de no crear archivos `_v2`/duplicados en brownfield. Mismo criterio aplicado al comando del Step 1/`unit-test-instructions.md` al ejecutar la suite final (ver más abajo).
2. **Path de test de `category_router.py`**: no existía ningún test previo para este router. El plan sugería `tests/unit/infrastructure/api/routers/test_category_router.py`, pero la convención real ya establecida en el proyecto para tests unitarios de otros routers es `tests/unit/api/routers/` (sin el segmento `infrastructure`, ver `test_admin_organization_contacts.py`, `test_image_router.py`, etc.) — usé la convención real.
3. **BR1.2 CASE 3 no es alcanzable con los datos actuales**: los 9 field_keys select-backed que `decode_vin()` reconcilia SIEMPRE tienen catálogo aplicable (`get_options()` nunca devuelve `None` para ninguno de ellos, por diseño — son exactamente los 9 field_keys que `FACEBOOK_VEHICLE_VALUE_CATALOG` cubre). La rama CASE 3 (`get_options() is None` → valor normalizado tal cual, sin agregar a `unmatched_fields`) está implementada tal como especifica `rules.md`/`functional-spec.md`, pero hoy es código defensivo sin caso real que la ejercite end-to-end desde `decode_vin()` — solo la ejercita directamente `test_facebook_vehicle_value_catalog.py::test_reconcile_field_key_without_catalog_returns_none`/`test_get_options_unknown_field_key_returns_none` sobre el domain service. Se activaría automáticamente si un futuro campo select-backed se agrega a `DecodedVehicle` sin agregarle catálogo.
4. **Tensión de diseño real encontrada en BR3.1** (documentada, no silenciada): dado que `accepted_raw_aliases` es la identidad de `canonical_value` (ver arriba, correcto y verificado para BR1.1/BR1.2), y el query de candidatos de la migración (`_find_candidates`) EXCLUYE explícitamente cualquier valor ya igual a un `canonical_value`, **`reconcile()` nunca puede matchear un candidato real de la migración** con el contenido actual del catálogo — todo candidato real quedará excluido por la guarda 2 ("no_catalog_match"), y la migración es, con los datos de hoy, funcionalmente un no-op seguro (excluye todo, no rompe nada). Esto no es un bug de implementación: es una consecuencia matemática de dos decisiones YA aprobadas en Functional Design (`entities.md`: aliases = tokens ya normalizados por `nhtsa_normalizer.py`, verificado al 100%; `rules.md` BR3.1: candidato = valor que no calza con ninguna `CanonicalFieldOption`). Para que BR3.1 migre algo en un entorno real, `FacebookVehicleValueCatalog` necesitaría aliases adicionales no-identidad (ej. variantes de casing de datos legacy pre-normalización) — eso está fuera del alcance de esta etapa (alteraría `entities.md`, ya READY) y queda señalado acá para una futura intent/decisión de producto. El test de "guarda 2 exitosa" (`test_upgrade_migrates_when_the_value_reconciles`) aísla la mecánica SQL de escritura/marcador del contenido real del catálogo vía `monkeypatch` sobre `reconcile()`, precisamente porque el camino "guarda 2 pasa con el catálogo real" no es alcanzable hoy.
5. **Logging de la migración ajustado durante Code Generation**: el primer borrador de `_do_upgrade()`/`_do_downgrade()` logueaba el valor capturado/nuevo (`%r`) en cada línea de resumen — corregido para NO loguear ningún valor de atributo, solo `product_id`/`field_key`/razón, al notar que contradecía literalmente `security-design.md` § NFR-SEC-4 ("nunca el valor de atributo completo en texto plano"). Corregido antes de terminar la etapa, no señalado como pregunta abierta.
