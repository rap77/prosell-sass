## Mecanismo de ejecución de la migración legacy (BR3.1) — corrección post-revisión

`rules.md` BR3.1 cita `20260812_0002_migrate_legacy_sedan_products.py` como precedente, pero ese precedente real es una **migración Alembic** (`revision`/`down_revision`/`upgrade()`), no un script standalone — corre automáticamente vía `alembic upgrade head`, ya invocado en cada deploy (`docker/api.Dockerfile:45` CMD del contenedor; `promote-prod.yml:53` antes de promover a producción). Siguiendo el mismo mecanismo que su propio precedente: **BR3.1 se implementa como un archivo Alembic nuevo** bajo `alembic/versions/`, no como un script manual separado — corre una sola vez (Alembic no re-ejecuta una revisión ya aplicada, tracker vía `alembic_version`), sin necesidad de runbook de acceso SSH manual ni de un mecanismo de invocación nuevo. Esto es consistente con "ejecución única, no un job recurrente" (BR3.1) y con "sin infraestructura nueva" (ya usa el mecanismo de deploy ya vigente).

## Shared Infrastructure

No aplica un recurso NUEVO compartido — U1 (backend) y U2 (frontend) ya comparten infraestructura preexistente no-nueva (mismo droplet self-hosted, mismo reverse proxy/dominio); la única relación NUEVA entre ambos es el contrato de API ya documentado en `contract-summary.md`, no un recurso de infraestructura.
