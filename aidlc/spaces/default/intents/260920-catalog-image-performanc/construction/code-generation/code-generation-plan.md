# Code Generation Plan — Catalog Image Load Optimization

## Scope, verified context, and pending decisions

This is one stage-level, brownfield `bugfix` iteration with the `minimal` strategy and the required `test-after` order. The plan covers the catalog's N+1 cover-URL fan-out, a private 600×600 thumbnail derivative, required CDN routing, cache-purge compensation, and frontend consumption.

Verified workspace facts shape the plan: `cover_image_key` already exists and selects an item from `image_urls`; `GET /products/{id}/image-urls` signs every gallery item after authorization and tenant-prefix validation; `DOSpacesService` signs against the configured public endpoint but does not read `do_cdn_endpoint`; and `useProductImageUrlsBatch` currently creates one React Query request per product.

The plan preserves private signed downloads and the existing defense in depth. It does not introduce a public bucket, a new permission, a CDN provider, or an unauthorised backfill. **Plan decision requiring approval:** retain the existing `cover_image_key` meaning and add a separate nullable thumbnail key only if required by the selected derivative persistence design; do not silently repurpose the existing gallery-cover key. This reconciles the requirement wording with the existing schema and migration.

**Unresolved requirements to decide during approved implementation:** OQ1 controls whether legacy rows receive a one-time backfill or use only the runtime fallback; OQ2 controls the explicit signed-download TTL; OQ3 controls the enforced batch cap and its error response. No value is assumed in this plan. If any remains unresolved at the point it is needed, implementation must stop and request that decision.

## Sequential plan and requirement traceability

- [ ] **Step 1 — Verify the baseline and scoped test runners.** Confirm mappings for `Product`, `ProductModel`, DTOs, and repositories; the existing signed-image endpoint and `_key_tenant_allowed`; `ImageOptimizer`, `image_router`, `IDOSpacesService`, Taskiq wiring, the products BFF proxy, and the `CatalogPage` → `useProductImageUrlsBatch` → `ProductCard` data flow. Run the exact scoped commands in `unit-test-instructions.md` before adding tests. **Traceability:** FR1–FR6, NFR1–NFR5; Minimal bugfix test obligations.
- [ ] **Step 2 — Implement the approved thumbnail persistence boundary.** Preserve `cover_image_key` as the gallery-cover selection. Add a nullable thumbnail-key representation through the domain entity, SQLAlchemy model, DTOs, and repository mapping only when the approved decision requires it; create a reversible Alembic migration only for a new column. Implement OQ1's chosen legacy behavior without changing `image_urls`. **Traceability:** FR2.3, FR2.5, NFR5.2, OQ1.
- [ ] **Step 3 — Test persistence after implementation.** Extend the existing product persistence tests to prove nullable thumbnail-key round trips, `cover_image_key` remains unchanged, and the selected OQ1 legacy path is used. If Step 2 creates a migration, add focused upgrade/downgrade regression coverage. **Traceability:** FR2.3, FR2.5, NFR5.2, OQ1.
- [ ] **Step 4 — Implement the private thumbnail derivative.** Extend `ImageOptimizer` with a centered square crop and exact 600×600 WebP output, then update `image_router` to upload that derivative without `make_public` and persist its selected key through Step 2's approved boundary. Preserve the current gallery WebP and public Open Graph JPEG behavior. **Traceability:** FR2.1–FR2.2, FR2.4–FR2.5, NFR1.3, NFR2.1.
- [ ] **Step 5 — Test the image pipeline after implementation.** Use in-memory Pillow fixtures with distinguishable center and edge pixels to prove exact dimensions, centered crop, WebP encoding, private upload arguments, thumbnail-key persistence, and no regression to gallery or Open Graph outputs. **Traceability:** FR2.1–FR2.2, NFR2.1.
- [ ] **Step 6 — Implement required CDN configuration and private signed URL routing.** Make missing or blank `do_cdn_endpoint` fail application configuration validation. Extend the storage port and `DOSpacesService` so the configured CDN host is used for signed private thumbnail and gallery downloads with OQ2's explicit TTL, while preserving the signature and never logging signed URLs or credentials. Validate the chosen CDN endpoint can serve the resulting signed request; do not replace signed access with a public URL. **Traceability:** FR1.5, FR3.1–FR3.3, NFR2.1–NFR2.3, NFR5.1, OQ2.
- [ ] **Step 7 — Test configuration and signed URL routing after implementation.** Add focused tests for fail-fast configuration, selected TTL, CDN-hosted signed thumbnail and gallery URLs, and unchanged tenant-prefix validation using fakes only. **Traceability:** FR3.1–FR3.3, NFR2.1–NFR2.3, NFR5.1, OQ2.
- [ ] **Step 8 — Implement the batch cover endpoint and response contract.** Add a typed batch request/response in `product_router` and adjacent DTOs, enforcing OQ3's selected limit. Reuse per-product authorization and `_key_tenant_allowed`; sign only the selected thumbnail or legacy cover fallback, not the gallery. Preserve `ORG_ADMIN_VIEW_ALL` cross-organization access while applying the same tenant-prefix validation. Emit structured `batch_size`, `user_id`, and `tenant_id` only. **Traceability:** FR1.1–FR1.4, FR2.4–FR2.5, FR6.1–FR6.2, NFR1.1–NFR1.2, NFR2.2, NFR4.1, OQ3.
- [ ] **Step 9 — Test the batch API after implementation.** Add the targeted N+1 regression at the narrowest effective API boundary: one batch request yields one cover per requested product, never gallery data. Cover legacy fallback, own-org and permitted cross-org access, unauthorized access, cross-tenant key rejection, selected OQ3 overflow behavior, and safe structured logging. **Traceability:** FR1.1–FR1.5, FR2.4–FR2.5, FR6.1–FR6.2, NFR1.1, NFR2.1–NFR2.2, NFR4.1, OQ3.
- [ ] **Step 10 — Implement cache invalidation and compensation.** Extend the existing image replacement/deletion paths to synchronously request CDN invalidation and storage deletion for the old key before a successful client response. When an operation fails after a successful new upload, retain the new image, record `queued_retry`, and enqueue an idempotent Taskiq retry using existing Redis-backed task infrastructure. **Traceability:** FR4.1–FR4.4, NFR3.1–NFR3.2, NFR4.2–NFR4.3.
- [ ] **Step 11 — Test invalidation and compensation after implementation.** With `AsyncMock`/fakes for the storage port, CDN client, and Taskiq broker, cover replace/delete success, purge failure after upload, queued retry, retry idempotence, and audit logs that expose outcome but no signed URL or secret. **Traceability:** FR4.1–FR4.4, NFR3.1–NFR3.2, NFR4.2–NFR4.3.
- [ ] **Step 12 — Implement the frontend batch consumer and compatibility fallback.** Replace the per-product `useQueries` fan-out in `productImageUrlsBatch.ts` with one validated batch request for the visible product IDs. Update its schema and `CatalogPage` mapping; keep `ProductCard` presentational and retain `next/image` `unoptimized`. When `cover_image_url` is absent, use the existing legacy `attributes.image_urls` fallback without another per-card fetch. Confirm the products BFF forwards the JSON batch body and authentication cookies. **Traceability:** FR5.1–FR5.4, NFR1.1, NFR2.1.
- [ ] **Step 13 — Test frontend behavior after implementation.** Update hook/component/proxy tests to assert exactly one batch fetch for visible IDs, no fetch for an empty list, validated degradation for malformed or failed payloads, thumbnail URL rendering with `unoptimized`, and legacy fallback rendering. **Traceability:** FR5.1–FR5.4, NFR1.1.
- [ ] **Step 14 — Run scoped quality checks and record delivery evidence.** Run the scoped backend and frontend tests, Pyright, Ruff, TypeScript, and ESLint commands from the unit instructions. Do not claim NFR1.2 or NFR1.3 without measured p95 evidence. After approved generation, create `source-manifest.json`, `code-summary.md`, and `traceability.json` with actual paths and results. **Traceability:** NFR1.1–NFR5.2.
