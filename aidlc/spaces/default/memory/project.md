## Deployment

<!-- Project-specific specialisation. -->

- El pre-commit local de este proyecto corre GGA (revisión de código vía codex) y puede tardar minutos (300s de timeout interno) — si el comando `git commit` se corta externamente (ej. timeout de la herramienta de shell) mientras GGA está corriendo, pre-commit ya ejecutó su paso de "[INFO] Stashing unstaged files to /home/rpadron/.cache/pre-commit/patch<timestamp>-<pid>" ANTES de correr los hooks, y como el proceso murió a mitad de camino, ese patch nunca se reaplica automáticamente — el working tree queda con esos archivos aparentemente "revertidos" (git status los muestra limpios). NO es pérdida de trabajo: el patch completo (diff exacto de los archivos no-stageados en ese momento) queda guardado en `/home/rpadron/.cache/pre-commit/patch<timestamp>-<pid>` — recuperar con `git apply --check <patch>` (dry-run) y luego `git apply <patch>`. Antes de reintentar un commit que timeouteó, correr `git status`/`git stash list` para detectar esta situación, y usar un timeout más largo (5-10 min) en el reintento dado que GGA ya es lento por diseño. (learned 2026-09-11) <!-- cid:260911-export-org-selector:deployment-execution:ae3781dd91f8d14161b8a9e3a035f36b7e242ef0b01c9e9285f345691685faf6 -->

- La migración Alembic del intent (`20260917_0001_migrate_legacy_vehicle_catalog.py`) corre automáticamente vía `alembic upgrade head` como parte del CMD del contenedor (`docker/api.Dockerfile`) en cada deploy — staging vía `docker compose up -d`, producción vía `docker exec prosell-prod-api python -m alembic upgrade head` en `promote-prod.yml`. No requiere coordinación manual separada del resto del deploy; el healthcheck del API pasando ya confirma que la migración corrió sin error. Confirmado en el intent 260915-vehicle-catalog (deployment-execution). (learned 2026-09-18) <!-- cid:260915-vehicle-catalog:deployment-execution:690625d76e1804031d0244951d2f7d19355ec325fb7616aa2d705c4f0116ea0f -->
- Al configurar rotación de logs de Docker (`logging.driver: json-file` + `max-size`/`max-file`) en `docker-compose.*.yml`, diferenciar los caps por volumen esperado de cada servicio en vez de un valor uniforme para todos: servicios que concentran log de negocio o access logs (ej. `api`, `caddy`) ameritan un cap más grande (ej. 20m×5=100MB) que servicios de bajo volumen salvo error grave (ej. `db`, `redis`, `minio`, 5m×2=10MB) o scripts de un solo shot (ej. contenedores de init, 2m×1=2MB). Confirmado en el intent 260915-vehicle-catalog (observability-setup) — un cap uniforme fue rechazado por el humano en favor de este criterio diferenciado. (learned 2026-09-18) <!-- cid:260915-vehicle-catalog:observability-setup:0a4f941e4cf534db2b06e24637b84df7dd01fca077d34feaab903ec3c1b8e79c -->

## Deviations

- En Deployment Execution (o cualquier stage con pre-commit real), cuando GGA bloquea el commit con hallazgos de seguridad en archivos tocados (aunque preexistentes y no relacionados con el objetivo del cambio), corregirlos antes de reintentar el commit — nunca usar --no-verify. Reconfirmado en 260911-cross-org-export-ux con 2 hallazgos reales (fail-open de tenant_filter en export_catalog_client_format.py; fuga cross-tenant de existencia de codigos de organizacion en bulk_upload_preview.py), ambos con fix + test de regresion agregados en el mismo commit. - En Performance Validation, cuando el volumen real de datos disponible (staging/prod) es muchisimo menor que el que describe un NFR de performance (ej. target a escala de plataforma vs 1 solo registro disponible), NUNCA reportar el NFR como PASS solo porque la medicion real quedó muy por debajo del target numerico -- el numero medido puede ser genuino pero irrelevante para lo que el target realmente describe. Documentar explicitamente como "no validable a escala real con los datos actuales", con el numero medido como piso informativo, en vez de fabricar un PASS sin sustento. Confirmado en 260911-cross-org-export-ux (NFR-PERF-4, target <18s a escala de plataforma, medido 0.324s con N=1 producto/1 organizacion).
